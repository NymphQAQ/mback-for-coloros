## 乘车码启动方式切换（2026-10-26）

在 **快捷小窗 → 乘车码启动方式** 选择，两种方式同时应用于微信和支付宝乘车码，更改自动保存，下次打开生效，无需重启：

| 方式 | 打开过程与依赖 | 兼容性 |
| --- | --- | --- |
| **负一屏启动（默认）** | 使用负一屏的乘车码入口，再将实际前台任务转换或恢复为系统小窗；可能先短暂全屏，需要负一屏正常工作 | 启动参数由负一屏维护，系统小窗转换仍依赖 ColorOS 接口及客户端容器活动 |
| **直接小窗启动** | 沿用此前已验证的独立实现，直接带系统小窗参数进入微信或支付宝；无需负一屏 | 微信使用私有 LaunchParcel，当前适配 8.0.79，更新可能需要重新适配；支付宝使用出行链接，也可能随入口变化而需要调整 |

扫一扫、付款码和其他应用的打开方式不变。两种模式共用原来的乘车码快捷项 ID、图标、排序及自定义图标，不需要重新添加。直接模式失败时可手动切回负一屏；不自动改写选择或跳转另一种方式。

配置键为 `Settings.Global.mback_transit_direct`：缺省或 0 为负一屏，1 为直接小窗，其他值回到负一屏。首次打开设置只读取缺省值，不主动写入。已打开的「更多应用」会随切换刷新预置项可用状态；直接模式检查客户端自身入口，不因负一屏停用而被判为不可用。

直接微信路径恢复了受 `STATUS_BAR` 权限保护的不绘制窗口 Activity，只接受 SystemUI 创建的一次性活动 PendingIntent；固定微信目标，校验微信签名后在 MBack 进程构造固定参数，不加载微信类到 SystemUI，不增加 Root 启动命令或 Xposed 作用域。负一屏模式不会调用该路径或加载微信参数类型；切换方式时停止旧方式的窗口等待。直接模式的窗口跟随只恢复已存在的原生小窗，修复微信重复打开后仍收起的情况，不执行全屏任务转换。

验证：本地构建与签名通过；一加 15 / ColorOS 17 上，`tests/transit_shortcuts_test.py` 最终整轮通过两种模式 × 两个客户端 × 冷启动/重复打开共 8 项，核对实际页面特征、原生窗口状态及输入焦点。直接模式四项均在负一屏停用时完成；同时验证缺省选择、互斥切换、自动保存、重开持久化、旧 ID、参数拒绝及权限边界。`tests/main_ui_test.py` 主页、分组设置、贴底导航、返回、保存及原生管理窗口回归通过。测试后恢复原配置、负一屏原启用状态和默认启动方式，移除临时测试包及文件；这些检查完成于 0.7.3 阶段，未在 0.7.4 重新执行。

观察记录：初轮组合检查曾出现一次负一屏支付宝重复打开仅回到主界面，随后单独冷/热启动及最终整轮均通过，未增加自动重试。未对其他客户端版本、其他 ROM、付款、开通或实际乘车核验作保证。

## 负一屏乘车码的系统小窗（2026-10-26）

- 原因：`windowingMode=100` 只作用于负一屏的短暂中转活动，后续微信 SDK / 支付宝出行活动会重新创建或复用自己的任务，原来的窗口选项没有继续传递。
- 保留两个负一屏中转组件、原快捷项 ID、图标、排序及参数。SystemUI 仅在 MBack 选择这两个预置项后，短时等待对应应用的实际前台活动，使用 ColorOS 原生任务接口把首次出现的全屏任务转换为小窗；复用已有小窗时通过系统任务恢复入口及 `mZoomLaunchFlags=2` 展开收起的窗口。
- 在负一屏模式下，运行时不加载微信 APK、不构造微信私有 LaunchParcel、不增加 Root 命令或额外 Xposed 作用域。新的 MBack 启动请求会取消旧请求，锁屏或通知栏展开时停止等待；等待最多 8 秒，转换失败时提示，线程在手势回调之外运行。
- 转换发生在负一屏完成跳转之后，可能看到短暂转场。适配使用了 ColorOS 系统接口和两个客户端的容器活动名称，系统或客户端以后更改这些入口时需要重新验证。
- `tests/transit_freeform_test.py` 已在一加 15 / ColorOS 17 真机通过：微信、支付宝的冷启动和重复打开均核对出行页面特征、原生窗口 `state=1`、未最大化及实际输入焦点，同时核对负一屏中转参与。两个直接启动负一屏中转页的对照测试继续保持全屏，修复仅由 MBack 的两个预置项触发。微信页面文案与负一屏自身启动对照，支持“乘车码”标题或包含公交、地铁、出行的页面特征。
- 测试不截图二维码，不付款、开通或乘车核验；原有快捷项和全部调节值已恢复，负一屏保持原启用状态。构建及签名验证通过，未重跑无关的完整图标、通知栏或主页面回归；该段记录对应 0.7.2 阶段，功能后续合入 v0.7.4。

## 实现

- 作用域为 SystemUI（com.android.systemui），Hook ColorOS 的 NavigationBarView。
- 原系统手势模式中 NavigationBar 的 touchableRegion 为空，因此旧 getevent 方案允许点穿。新版本使用 OnComputeInternalInsetsListener 在系统导航栏增加有限的可触区域，通过 ViewGroup.dispatchTouchEvent 消费点击。v0.3 曾扩大为导航栏窗口完整厚度；当前竖屏按系统导航栏高度收紧，仍覆盖屏幕下沿，避免抢走应用底部按钮。只在白条附近的长轴中间区域捕获。
- 触摸区域以 SystemUI 当前导航栏布局及可见 NavigationHandle 为准，跟随屏幕旋转，不硬编码触控芯片的竖屏坐标。
- v0.3 的 0–380ms 短按、移动不超过 22dp 时通过 InputManagerGlobal 注入 BACK；取消了对极短点击的过滤。SystemUI 已具备 INJECT_EVENTS 权限。
- 滑动、多指、长按不触发返回；导航栏的上滑仍由系统的 gesture monitor 处理。
- 可设置小白条轻点时的缩放比例（50%～150%，每档 5%）、缩放总时长（80～500ms，每档 20ms），点击确认后先缩放再恢复。100% 相当于没有缩放幅度。
- 支持振动强度 0（关闭）及 1～10 级（10 档不同振幅），并提供“试听当前震动”按钮。硬件支持振幅控制时使用单次 VibrationEffect 自定义振幅，成功轻触时才触发。参数在 Xposed 的 SystemUI 进程通过 Settings.Global 观察并动态更新，不需要重启。
- 有“启用轻触返回”和“显示常驻状态通知”两个独立开关。关闭通知不会停止手势功能，无后台 getevent 进程，也不需要前台 Service。
- 开关通过 root 写入 Settings.Global.mback_xposed_enabled，SystemUI 监听变更动态更新触摸区域；设置值在触摸回调之外缓存，降低每次触摸的开销。

## 本地构建和安装

需要 JDK 17+、Android SDK 35、Build Tools 36。本机使用零第三方依赖构建脚本：

```bash
bash build-local.sh
adb install -r app/build/local/mback-debug.apk
```

stubs/ 下只有编译期 legacy Xposed API 的声明，脚本不会把这些 stub 打包进 APK。运行时 API 由 Vector / LSPosed 提供。

## 启用方式

1. 安装 APK。
2. 在 Vector（或兼容 Legacy Xposed 的 LSPosed）中启用 dev.mback.oneplus，作用域设置为 com.android.systemui 与 com.android.launcher（后者用于拦截多任务前段）。使用全局系统小窗控制时还需勾选“系统框架”（Vector CLI 中记作 system）。
3. 普通更新重启 SystemUI 或手机；首次添加系统框架作用域必须重启手机。
4. 打开 MBack，默认开启“轻触返回”和“底角快捷小窗”，修改设置时需要 root 授权。
5. 按需开启“显示常驻状态通知”。若通知不显示，请核实通知权限及“MBack 状态”渠道。

本机 Vector 命令：

```bash
adb shell su -c '/data/adb/lspd/cli modules enable dev.mback.oneplus'
adb shell su -c '/data/adb/lspd/cli scope add dev.mback.oneplus com.android.systemui/0'
adb shell su -c '/data/adb/lspd/cli scope add dev.mback.oneplus com.android.launcher/0'
# 仅全局系统小窗功能需要，添加后重启手机
adb shell su -c '/data/adb/lspd/cli scope add dev.mback.oneplus system/0'
```

## 系统小窗设置（本地开发版 0.7.5）

入口：**快捷小窗 → 系统小窗设置**。控制本机主屏幕上的 ColorOS 原生应用小窗，包括从系统侧边栏、桌面等其他入口打开的小窗；不控制画中画、悬浮球或第三方悬浮控件。

- **统一默认位置**：缺省关闭，沿用系统原行为。开启后，横向和纵向分别按可用剩余空间的 0–100% 定位，50% 为居中；保持系统窗口大小和缩放比例，并避开状态栏、导航栏和系统侧面安全边距。位置在下次打开或恢复标准小窗时应用，已展开的小窗仍可手动移动。
- **打开位置预览小窗**：打开一个真实的系统小窗，使用与其他应用相同的定位逻辑。改变设置后关闭并重新打开预览；页面计数可检查收起再恢复是否保留状态。

- 作用于当前展开的原生小窗；触摸任一小窗内部不关闭其他小窗。滑动、长按、多指不触发收起；键盘、通知栏、锁屏和屏幕边缘手势不受影响。

## 左右下角触控死区修复（2026-10-24）

- **原因**：快捷小窗长期放置的透明拦截区高达屏高的 6.5%，在一加 15 上是两块 `242×180px` 的区域，覆盖了系统导航栏上方的应用按钮。关闭快捷小窗后，相同位置的四次点击均恢复，小白条返回保持开启。
- **触控与识别**：透明拦截区仅覆盖系统 `navigation_bar_height`，本机为两块 `242×48px` 的区域，位于 `[0,2724]—[242,2772]` 和 `[1030,2724]—[1272,2772]`。菜单、SystemUI 和 Launcher 共同识别更宽松的下角 **48dp** 范围；这个范围只旁听普通触摸，确认向内斜滑后才调用 `pilferPointers` 取消下层应用的触摸并接管本次手势，避免扩大死区。
- **连续呼出**：每次新的 `ACTION_DOWN` 清理旧菜单并重新识别起点；松手、取消或多指打断均结束当前菜单。无需紧贴物理底边，在左右下角向内斜滑即可。
- **回归**：`CornerGestureTest` 覆盖 32 项断言，`HitZoneTest` 覆盖 15 项断言。`python3 tests/corner_touch_test.py` 检查两侧应用按钮点击、识别范围外滑动不呼出菜单、底边及距底边 32dp 连续斜滑、松手关闭和取消后再次呼出，并确认没有点击穿透；测试结束保留原配置。真机左右两侧滑开菜单时，下方系统设置列表的既有条目位移均为 0px；选择“更多”后，在该浮窗上从距底边 44dp 处仍能再次呼出。通知栏底部上滑、左右切换和小白条反馈也有独立回归脚本。
